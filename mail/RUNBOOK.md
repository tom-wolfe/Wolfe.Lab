# mail runbook

## First login (one-time, at the desk)

Bridge needs a password, a second factor and the mailbox password, so
this cannot be a job. It is done once per volume and survives restarts,
reboots and redeploys.

Two machines are involved, and which one runs what is not incidental:
**the mini's 1Password credential is a read-only service account**, so
every item is created from a workstation where you are signed in
interactively. The mini only ever reads.

**1. On your Mac** — the keyring passphrase, which encrypts the GPG key
guarding the stored session. Generated by 1Password rather than chosen:

    op item create --vault Wolfe.Lab --category "API Credential" --title proton-bridge-keyring --generate-password=64,letters,digits

**2. On the mini** — the login itself. The service-account token has to
be in the environment or `op` has no credentials and simply waits
forever; the volume name is the one compose will use:

    ssh macmini.local
    export OP_SERVICE_ACCOUNT_TOKEN="$(cat ~/Docker/1password/service-account-token)"
    docker run --rm -it \
      -e KEYRING_PASSPHRASE="$(op read 'op://Wolfe.Lab/proton-bridge-keyring/credential')" \
      -v mail_bridge:/root \
      dancwilliams/protonmail-bridge:v3.26.0-4 init

At the `>>>` prompt: `login`, and answer what it asks. Then read back the
credentials a mail client would use, and leave:

    info
    exit

`info` prints a username and a password. They are Bridge's own, not the
Proton account's, and they are what the watcher authenticates with.

**3. On your Mac again** — store them, as their own item:

    op item create --vault Wolfe.Lab --category login --title proton-bridge username=<the username> password=<the password>

Then deploy the slice — merge, or `lab deploy` from `mail/compose/` in a checkout
on the mini.

## Check it is serving

Bridge publishes no host port, so this is asked from inside the network
it serves:

    ssh macmini.local
    docker run --rm --network lab busybox nc -z -w 5 bridge 143 && echo open

A refusal means bridge is running but has not finished starting, or the
login never happened. Its own account of itself:

    docker logs --tail 50 proton-bridge

## The watcher

Its state directory has to exist and be writable by the container, which
runs as the host user. Once, at the desk:

    ssh macmini.local
    mkdir -p ~/Docker/mail/watcher

What it is doing:

    docker logs -f mail-watcher

A healthy start says which host it is watching and where it resumed from.
After that it is quiet until mail arrives — silence is the normal state,
not a symptom.

## What the watcher decided

Every message it looked at is accounted for by the watermark, so "did it
see that email" is answerable:

    ssh macmini.local
    cat ~/Docker/mail/watcher/watermark.json

`lastUid` is the highest message it has finished with. A message with a
lower UID has been dealt with — either an invitation was sent, or it
found no event, and the logs say which.

To make it re-read recent mail, stop the watcher, lower `lastUid`, start
it again. To make it forget everything and resume from now, delete the
file: the next start takes the current UID as the mark.

    docker stop mail-watcher
    rm ~/Docker/mail/watcher/watermark.json
    docker start mail-watcher

## No invitation arrived

In the order worth checking:

    docker logs --tail 100 mail-watcher

A message it skipped as "already an invitation" is Proton's to handle,
not a fault. "No event in ..." means both tiers declined — for prose that
is the model's answer, and the model is only as good as it is.

If nothing is logged at all, it is not seeing the mail: check the
watermark has not run ahead, and that bridge is serving.

    docker run --rm --network lab busybox nc -z -w 5 bridge 143 && echo open

If the model tier is the suspect, ask it the same question by hand:

    curl -s https://ai.twolfe.dev/api/tags

## When the login expires

Bridge sessions do not last forever, and the symptom is the watcher's
authentication failing rather than anything here looking wrong. Re-run
the first-login block above; the volume is reused and nothing else
changes.

## Upgrading

Bump the `image:` tag in `compose.yaml` and redeploy. Check the fork's
releases first — it tracks upstream Proton Bridge, and falling far behind
is what gets a Bridge version refused by Proton rather than merely dated.

    https://github.com/dancwilliams/protonmail-bridge-docker/releases
